## 3. Architecture Validation Report

### System Boundaries

✅ Architecture diagram: Astra-only block, no prati
✅ AppState contract table: all fields correct
⚠️ Architecture diagram: shows only `ApiService / Repository` — missing `IpcService`
⚠️ Project structure: missing `IpcService.ts`, `types.ts` (ITransportService, Platform), `apiServiceFactory.ts`

**New: README-ARCH-001** | Minor — Architecture diagram does not reflect the dual-platform Repository pattern (missing IpcService)

### Architectural Drift

**New: README-IPC-003** | **Major** — The Electron Quick Start example (lines 144–173) uses `window.electronAPI.getSettings()` directly in a repository object. This violates the architectural rule stated both in the README's own MVVM Rules section ("Repositories use ApiService — never import axios directly" / feature doc says "never import window.electronAPI directly") and in three architecture docs: `mvvm-wiring.md` ("Feature repositories must use ApiService or IpcService — never import axios or window.electronAPI directly"), `repository.md` ("Use IpcService for IPC calls"), and `platform-abstraction.md` ("Repositories consume IpcService, never raw window.electronAPI").

Impact: Consumers learn the wrong pattern from the most prominent Electron example. Code written following this example will work at runtime but bypass IpcService's error normalization and fail architecture compliance review.

Fix: Replace the repository example with IpcService:
```tsx
import { IpcService } from "astra";

const ipc = new IpcService();
const settingsRepo = {
  get: (): Promise<ServerResponse<Settings>> =>
    ipc.invoke("settings:get"),
};
```

### Source Discrepancies (previously noted)

The previous audit noted two non-README issues:

1. **`HttpStatusCode.IDLE = 1000` in architecture docs** — `docs/raw/architecture/core/repository.md` (line 144) and `docs/raw/architecture/core/state-management.md` still show `HttpStatusCode.IDLE`. Feature doc says `StateCode.IDLE` (not HttpStatusCode). Still open; outside README scope.

2. **INTERNET_ERROR source bug** — Previously, `ApiService.ts` network-failure path fell through to `INTERNAL_SERVER_ERROR (500)` instead of `INTERNET_ERROR (0)`. **This has been fixed** in the current source (confirmed: `axiosError.response?.status ?? HttpStatusCode.INTERNET_ERROR`). Resolved.
